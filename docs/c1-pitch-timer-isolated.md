# C1一球管理と投球タイマーの隔離接続（2026-10）

## 結果と範囲

`node tests/pitch-timer-contract.cjs` は `index.html` から `pitch()` と `startPitchMotion()` の関数テキストを読み込み、変更せずVMで実行する。仮想時計を `setTimeout/clearTimeout` として注入し、前工程の `tests/pitch-contract-isolated.cjs` のC1管理器・固定seed乱数・模擬成績を利用する。`drawPitch`、`resolvePitch`、守備位置調整、リード動作、牽制動作、球種選択、作戦、次投球scheduleはモック。結果確定時には実試合エンジンを呼ばず模擬カウントと成績を更新する。既存の投球タイマー分岐は再利用したが、実ブラウザ・SVG・実ゲームの作戦や投手交代・リアルタイム動作は検証していない。

試験アダプターは `startPitchMotion()` の入口を包み、作戦完了を模擬してから元の関数を実行し、`drawPitch` モックでC1一球を生成して表示側が取得し、既存完了タイマーから `resolvePitch` モックで同じデータを確定する。作戦成立のケースは固定値であり、本物の `tactics()` を実行したわけではない。再開タイマーは試験用であり通常ゲームのpause/resumeではない。`choose` は先頭固定で球種抽選の乱数は未検証。既存ゲーム内でのC1生成や、前工程の実試合C1接続とタイマーの結合はまだ未検証。

## 現行順序と時刻

- `pitch()` は試合未開始・終了・`flightTimer` 使用中なら開始しない。走者がいる場合、確率0.008で牽制し、牽制の演出時間+110ms後に必要なら次をschedule。投球は生成しない。
- 牽制以外は守備配置の移動、走者がいて乱数条件が成立すればリードを開始。長い方の演出時間+90ms後に `startPitchMotion()`。
- `startPitchMotion()` は球種を選択し `drawPitch()` を開始。`drawPitch` はanimationTokenを増やし、投球モーションと540msの予備動作後に飛行。540ms+球種別320〜630ms+110ms後に `resolvePitch()`、継続中なら `schedule()`。スイングや見送り演出は `resolvePitch()` 内で呼ばれる。
- `resolvePitch()` 冒頭で作戦、成立すればイニング終了・投手交代など。作戦がなければ投球数・結果・カウント・必要な打球、走塁、イニング終了、盗塁、投手交代を処理。次球scheduleは速度、演出保留時間等に依存する。

例えば隔離試験Aは守備配置100ms+90msで190msに描画開始、ストレートの540+320+110=970ms後、開始から1160msに確定した。リード300msのケースは390msに開始。牽制は仮の演出300ms+110ms。実際の守備・牽制演出時間は入力条件で変化する。

## 固定ケース

|ケース|隔離試験|結果|
|---|---|---|
|A|準備後に生成、元の完了タイマーで同じデータを模擬確定|PASS|
|B|現行 `pitch()` の牽制分岐後に新投球、牽制中はC1未生成|PASS|
|C|描画中取消後、取消済みcallbackを人工的に発火しても無反映|PASS|
|D|描画中断・試験用タイマーで同じ一球を再開|PASS、タイマー参照の問題あり|
|E|投手・打者の模擬ID変更後に旧完了タイマー発火、失効|PASS|
|F|完了処理を二度呼び、二重加算なし|PASS|
|G|完了後の次投球で新IDを発行|PASS|

管理器のC1乱数は生成時のみ消費、再描画・再開・取消・二重要求では消費しない。牽制分岐自身の現行乱数は消費する。C1生成後取消は乱数を巻き戻さない。固定seedのデータ・成績・C1乱数回数の一致を確認した。画面や実成績の反映で同様の保証があるという意味ではない。

**重要な境界条件**：現行投球完了callbackはtokenの検査より先に `flightTimer=null` を実行する。取消済みの古いcallbackを人工的に遅延発火させたところ、新タイマーの参照を消せた。古いcallbackが描画・成績を更新することはtokenと管理器で防げたが、参照が消えると次の取消や重複開始の防御に影響し得る。この再現は仮想時計で取消済みcallbackを直接実行した故障注入であり、通常のブラウザで必ず発生するとの証拠ではない。実接続ではtoken・タイマーIDを確認してからそのタイマーだけを解除する設計と、実タイマー競合の検証が必要。

## 例外・部分反映

独立した非原子的な模擬更新に例外を注入した。確定前は変更なし、カウント更新後はカウントのみ変更、投球成績更新後は両方変更される一方で確定済みフラグは未設定となった。これは一般的な部分更新の危険を示す実験で、本番に実際にその障害が起きたことを示さない。

先に確定済みを記録すると途中失敗時に欠損、最後に記録すると途中失敗後の再試行で二重加算する危険がある。試験管理器の模擬更新は次状態を先に作り同期反映するが、既存 `resolvePitch()` は複数関数・描画・乱数・走塁・得点へ副作用を持つため、そのままで原子性を保証できない。実接続の前に結果の準備と確定の境界、再入防止、部分失敗時の復旧や冪等性を設計し、作戦・得点・走者まで含む故障注入が必要。

## 描画と次工程

正規化投球位置を既存 `drawPitch()` の終点へ投影する契約、左右打者の内外・高さ、球種の途中軌道、捕手の受球位置を定める。同じ記録のzone/outcome/swingをストライク・ボールと `animateBatterTake/animateBatterSwing` に渡す。俯瞰SVGでは高さと奥行きが混在するので線形変換を前提にしない。現在の作戦順序・pause動作・タイマーを変えずに実接続できるとはまだ言えず、通常画面への接続は保留。実エンジンの作戦・牽制・投手交代、例外処理を含む隔離接続を先に検証する。

C1・B2mは本番未採用。外野捕球、ライナーバウンド、二遊間位置、H/E表示、死球処理も未解決。本番コード、確率、RNG、画面、保存形式は変更していない。
